# Visual editing troubleshooting

Symptoms you hit when editable regions do not appear, do not update, or write to the wrong field. Region types and the attribute reference live in [editable-regions.md](editable-regions.md); the patterns behind these fixes live in [visual-editing-reference.md](visual-editing-reference.md); deeper lifecycle traces live in [editable-regions-internals.md](editable-regions-internals.md).

Astro-specific rows are in [astro/troubleshooting.md](astro/troubleshooting.md).

## Regions that do not appear or bind

| Symptom / mistake                                                 | Fix                                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Used `data-editable="content"`                                    | Not a valid region type. Valid types: `text`, `image`, `array`, `array-item`, `component`, `source`. For the markdown body use `data-editable="text" data-type="block" data-prop="@content"`.                                                                                  |
| "Text editable regions require a 'data-prop' HTML attribute"      | A text region has no `data-prop`. For plain-string array items this is expected — pass `data-prop=""` to bind the item's own scope. See [Array editing](visual-editing-reference.md#array-editing).                                                                            |
| An `<editable-component>` renders no edit button                  | Its `data-prop` is an empty string, which the component controls UI treats as falsy. Point it at a real key, or nest the frontmatter so there is one. See [Empty `data-prop` pass-through](visual-editing-reference.md#empty-data-prop-pass-through).                          |
| Region errors on some pages but not others, on a shared component | The field is absent from the data scope on those pages. Guard the region, or gate it on an optional prop naming the path. See [Conditional editable-image](visual-editing-reference.md#conditional-editable-image-on-shared-components).                                       |
| A region on an optional field errors when the field is empty      | CloudCannon inspects the resolved value at initialization. Conditionally render the element. Note that content-sourced objects and empty arrays are truthy — guard on inner fields and length. See [Guard optional fields](visual-editing-reference.md#guard-optional-fields). |
| Editable text has nowhere to attach                               | The region needs a single concrete DOM element as its host. A construct that emits no DOM node, or a component with multiple roots, has no host. Use one wrapper element. See [Text editing](visual-editing-reference.md#text-editing).                                        |
| Block content breaks the DOM around a region                      | `<p>` cannot nest `<ul>`/`<ol>`/`<h*>` — the browser auto-closes it. Host `data-type="block"` on an element that can hold block content. See [Text editing](visual-editing-reference.md#text-editing).                                                                         |
| A camelCase field never binds through `data-prop-*`               | `data-prop-*` lowercases its key, so `data-prop-pubDate` looks for `pubdate`. Bind an object with `data-prop`, or rename the field. See [Data-prop paths](visual-editing-reference.md#data-prop-paths--pick-one).                                                              |

## Arrays

| Symptom / mistake                                                            | Fix                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Array item editable regions must be nested inside an array editable region" | Double nesting — a registered component's own output starts with an `array-item` element while CloudCannon has already wrapped it in one. The array-item wrapper belongs in the page template. See [Page builder blocks](visual-editing-reference.md#page-builder-blocks).                        |
| CRUD controls attach to the wrong elements, or a static child errors         | A static sibling sits inside the `data-editable="array"` wrapper, which treats every direct child as an item. Split the layout container from the array container. See [Don't mix array items with non-array siblings](visual-editing-reference.md#dont-mix-array-items-with-non-array-siblings). |
| Child editables in a data-file array resolve to undefined                    | An indexed path (`@data[footer].columns[0].heading`) escapes the item scope. Children use relative paths; the `@data[...]` prefix appears only on the parent array. See [Arrays inside data files](visual-editing-reference.md#arrays-inside-data-files).                                         |
| "Add item" produces an empty or broken row                                   | The array has no `<template>` blueprint and no registered component to render from. Author a `<template>` mirroring the live item. See [When HTML `<template>` blueprints are needed](visual-editing-reference.md#when-html-template-blueprints-are-needed).                                      |
| Sub-array items inside a widget have no inline CRUD controls                 | The sub-array is missing `data-editable="array"` / `array-item`. It does not need `data-component`. See [Sub-arrays within widget components](visual-editing-reference.md#sub-arrays-within-widget-components).                                                                                   |

## Values that do not update

| Symptom / mistake                                                                       | Fix                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Put defaults in template `\|\|` fallbacks instead of schema frontmatter                 | `data-editable` regions display the stored field value, not the rendered HTML. Empty or missing field plus a template fallback means production renders the default while the editor shows blank. Put defaults in the collection schema, and in structure-value defaults for page-builder blocks. Keep a `?.trim() \|\|` safety net for legacy entries, and backfill content.                                                           |
| Changed a schema default without backfilling existing content                           | `data-editable` shows the stored value. Existing entries keep the old, often empty, value; only new entries get the new default. Pair the schema change with a backfill.                                                                                                                                                                                                                                                                |
| A field's rendered output is a computed expression and a text region does not update it | A primitive region updates DOM text only — it cannot re-run the expression. Wrap the section root in `<editable-component>`. See [Golden rule](visual-editing-reference.md#golden-rule--computed-content-needs-a-component-wrapper).                                                                                                                                                                                                    |
| A value read from a shared data file does not live-update                               | Lookups bake at build time. Either read the lookup inside a registered component wrapped in `<editable-component>`, or address the value directly with `data-prop="@data[<key>].dotted.path"`. Do not use `data-editable="source"`. See [Shared-data handling](visual-editing-reference.md#shared-data--computed-content-handling).                                                                                                     |
| Used `data-editable="source"` with `data-path` / `data-key` for a shared-data field     | Wrong semantics. Use the region type you want with `data-prop="@data[<key>]..."`, where `<key>` is registered in `data_config`. `@data[<key>]` routes through the same channel as frontmatter edits.                                                                                                                                                                                                                                    |
| A sidebar switch or dropdown does not trigger a re-render                               | Either the component is self-marked on its own root instead of wrapped at the call site, or its fields are scattered at the frontmatter root with no single `data-prop` to point at. See [Registration placement](visual-editing-reference.md#where-does-the-registration-go--component-root-or-call-site) and [Nested frontmatter](visual-editing-reference.md#scattered-fields-feeding-a-registered-component--nest-the-frontmatter). |
| Editing a statically-placed section mutates a top-level field instead of the nested key | The component is registered but missing its `<editable-component data-component="<name>" data-prop="<key>">` wrapper. A prop that builds `data-prop` strings at compile time is the wrong fix — the component still never re-renders on field change. Wrap it, and remove the prefix helper.                                                                                                                                            |
| A field is missing from the props of a re-rendered component, though it builds fine     | The CloudCannon schema file for the collection gates which fields are forwarded on re-render. A hidden `_input` does not fix this — `_inputs` control sidebar UI only. Add the missing key, with a default, inside the correct nested object in the schema file. See [Schema file gates prop forwarding](visual-editing-reference.md#schema-file-gates-prop-forwarding-on-re-render).                                                   |
| Registered the component and expected inline editing to work                            | Registration enables component re-rendering and page-builder instantiation. Inline editing still needs `data-editable` attributes on every rendered text and image field, and array regions on every list. These are independent concerns.                                                                                                                                                                                              |

## The editor's own rendering

| Symptom / mistake                                                   | Fix                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blocks fade out or vanish on editor load, or after editing a field  | Scroll-reveal CSS. Re-rendered nodes get the hidden styles but not the JS-applied active class. Override with `.cms-editor-active` in global CSS. See [Scroll-reveal and entrance animations](visual-editing-reference.md#scroll-reveal-and-entrance-animations).                                    |
| An attribute inside a rich text region disappears, or is uneditable | Rich text contents are parsed into the editor schema and re-serialized, which does not preserve arbitrary attributes. Move the attribute to the region host. See [editable-regions.md § Rich text region contents are editor-owned](editable-regions.md#rich-text-region-contents-are-editor-owned). |
| Build-only logic runs, or fails, inside the editor's client bundle  | Branch on `ENV_CLIENT`, which is true only in that bundle. It does not affect the initial production render — use `.cms-editor-active` for that. See [Detecting the editor](visual-editing-reference.md#detecting-the-editor-and-skipping-build-only-logic).                                         |
