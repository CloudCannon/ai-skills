# Visual editing troubleshooting (Astro)

Astro-specific rows only. Generic symptoms are in [../troubleshooting.md](../troubleshooting.md) — check there first.

| Symptom / mistake                                                                               | Fix                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assumed a component registered in `componentMap.ts` would live-update in the editor             | Registration only enables page-builder instantiation as a `_type` block. Inline live-editing still requires `data-editable` attributes on every rendered text/image field, and `data-editable="array"` + `array-item` + nested `text` on every `.map()`. Independent concerns.                                                                                                                        |
| `Cannot destructure property 'x' of 'n.props' as it is undefined` in `registerComponents.*.js`  | Scattered root-level frontmatter fields with no single `data-prop` to point at. Reshape the Zod schema to nest them under one object key. See [Scattered fields](visual-editing-reference.md#scattered-fields--the-zod-reshape).                                                                                                                                                                      |
| Component renders fine in `astro build` but a field is missing from `Astro.props` in the editor | The CloudCannon schema file (`.cloudcannon/schemas/<collection>.md`) gates prop forwarding. A hidden `_input` in `cloudcannon.config.yml` does NOT fix it. Add the missing key with a default inside the correct nested object. See [the Astro diagnosis](visual-editing-reference.md#schema-file-gates-prop-forwarding--the-astro-diagnosis).                                                        |
| Multiselect of refs renders nothing or renders all — selection appears not to work              | `reference()` fields are `{collection, id}` objects at runtime, not strings. `entry.id === ref` is string-vs-object and always false. Use `getEntry(ref)` for one ref, or `entry.data.x.some(r => r.id === currentId)` for membership. Type props as `{collection: string; id: string}[]`, never `string[]`.                                                                                          |
| Multiselect appears to work but selection is ignored — same output regardless                   | The component has an `if (length === 0) showAll` fallback. Combined with a ref-comparison bug the filtered array always empties, so the fallback always fires. Remove it — an empty array should render nothing. Seed defaults in `.cloudcannon/schemas/<collection>.md`.                                                                                                                             |
| Slug change in a `reference()`-backed array doesn't update the card's name or image             | `await getEntry(ref)` resolves at build time and CloudCannon can't re-resolve refs client-side. Either wrap the parent section in `<editable-component>` so it re-renders on array change, or restructure items to carry inline-editable fields alongside the ref.                                                                                                                                    |
| A React island shows an error state in the editor                                               | Open the editor iframe's dev tools console. Almost always: `fetch` failing because there is no server, a missing required field, or a hydration mismatch.                                                                                                                                                                                                                                             |
| `NoMatchingRenderer` during re-render                                                           | A React component inside a registered Astro component with no React renderer loaded. Add `import "@cloudcannon/editable-regions/astro-react-renderer"` to `registerComponents.ts`, after any other framework renderers.                                                                                                                                                                               |
| A Vue, Svelte or Solid component errors in an editable region                                   | There is no renderer for those frameworks. Convert to `.astro` or React, or provide an editing fallback. See [Non-Astro framework components](visual-editing-reference.md#non-astro-framework-components).                                                                                                                                                                                            |
| `data-prop` not resolving, or shows blank in the editor                                         | `data-prop` paths resolve via `CloudCannon.currentFile()` against the markdown source mapped through the collection's `url` config — not against `Astro.props`. Check the collection's route `url` in `cloudcannon.config.yml`, that the field path exists in the frontmatter, that a parent `data-editable` ancestor exists, and that `data-component` matches the key in `componentMap.ts` exactly. |
| An `<Icon>` build fails with `Unable to load the "local" icon set!`                             | `astro-icon` always tries to load `src/icons/`. Create the directory, even empty. See [astro-icon](visual-editing-reference.md#astro-icon).                                                                                                                                                                                                                                                           |
| An `<Icon>` build fails with `Unable to locate "" icon!`                                        | A `<template>` blueprint passes an empty icon name and Astro renders template contents server-side. Guard on a truthy name: `{icon && <Icon name={icon} />}`.                                                                                                                                                                                                                                         |
